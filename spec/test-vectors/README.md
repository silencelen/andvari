# Test vectors — provenance manifest

These 35 files are the shared corpus every implementation is graded against: the Kotlin
reference (`core/`, jvmTest), the web TypeScript engine (`web/`, vitest), and the
extension's @noble engine (`extension/`, `node --test`). `scripts/verify.sh` greens all
three suites off *these* bytes, so a divergence in any engine reds that engine rather
than quietly forking the fleet.

**The corpus has two provenances**, and an auditor should be able to tell them apart.
`tools/vector-gen` emits 17 of the files from the Kotlin reference implementation — those
are *derived* artifacts and are regenerated when the spec changes. The other 18 are
**hand-authored**: they encode classification/parsing decisions and corpus-derived
fixtures that no generator produces, so they are edited deliberately, by hand, as part of
the change that needs them. Neither kind may be edited casually — a vector edit is a
fleet-wide behaviour change and is reviewed as one, and the crypto vectors in particular
are held byte-identical across releases so a regression cannot hide behind a regenerate.

reference implementation named in each row.

> **⚠ THE GENERATOR IS BEHIND THE CORPUS FOR TWO FILES — do not regenerate wholesale
> (measured 2026-08-23).** Running `vector-gen` over this directory today would silently
> **delete committed test cases**:

>
> Until `vector-gen` is taught those cases, regenerate to a **scratch directory** and copy
> across only the file you intend to change. Rule 2 below ("generated files are rewritten
> wholesale") states the danger; this states where it has already come true.
>
> Separately and benignly: `seal.json`, `secretstream.json` and `sharedgrant.json` differ on
> **every** run by construction — sealing and secretstream headers are randomized, and those
> vectors are verified in the DECRYPT direction rather than by byte-comparison. A diff in
> those THREE is not drift. **`export.json` is NOT one of them** (audit H95, 2026-09-13): its
> containers take a fixed salt and an injected nonce and are byte-exact by spec 07 §4, so a
> diff there IS a behaviour change. This paragraph used to list it among the random four,

> `check`/`dupeAck` to the item document and the generator's payload, the corpus was never
> regenerated, and both consumers decode the payload semantically so nothing reddened).
> Regenerated 2026-09-13, with a third container case that carries both v9 fields populated.
>
> `sharedgrant.json`'s `rejectVkLength` case (H93) and `rejectVersion` case (recheck R48 —
> the payload-version refusal, the third of spec 01 §6's recipient checks) were added by
> regenerating to scratch and splicing ONLY the new key into the committed file, so the frozen
> `sealedB64` bytes every engine already opens stayed byte-identical. That is the procedure for adding a case to a
> randomized file: never a wholesale regenerate, which would silently re-mint every seal.

## Onboarding and trust vectors (independent oracle)

These files pin the formats of `docs/design/2026-11-15-onboarding-trust.md` (§17 is the plan). They are
**hand-authored from an independent oracle**, `tools/vector-gen/oracle/`: a Node program written from
the design text alone, with Node's WebCrypto, `@noble/ed25519`, `@noble/curves`, `@noble/ciphers` and
`@noble/hashes` at pinned versions, and **no andvari code**. Every seed, key and nonce in it is a
constant, so two runs give byte-identical files.

- `npm ci && npm run generate` in `tools/vector-gen/oracle/` rewrites the files below. It is not the
  Kotlin `tools/vector-gen`, and it writes no other file.
- `npm run check` regenerates into a scratch directory and fails on any difference from the committed
  files. It also grades every committed row with the oracle's own verifiers (each rejection row must
  get exactly the verdict it names), recomputes every hash, MAC, key derivation and signature with
  WebCrypto, and checks the primitives against `seal.json`, `envelope.json`, `signedstatement.json`
  and `wrap.json` for the conventions the design leaves unchanged.
- A row is changed by changing the design first, then the oracle, then regenerating. A red row in an
  engine means the engine and the oracle read the design differently: settle the reading, never the row.

### The key floor rows

Rule 4 of spec 01 "Keys in memory and the lock" says that no legitimate key is all zeros, so a
client refuses one before the platform's crypto provider is called. Until 2026-11-16 three normative
rows derived values from an all-zero input; the shared code refused them while the TypeScript clients
derived them, so the implementations no longer meant the same thing by those rows. Each of the three
now holds the near-zero input (31 zero bytes and one 0x01, the lowest input the floor accepts), which
the oracle derives by itself and which equals the Kotlin implementation's values byte for byte. The all-zero
inputs moved to `keyfloor.json` as rows that say "this must be refused". It is a file of its own so
that no runner that reads the three old files meets a row it would have to refuse.

Who grades it today: **core** (`KeyFloorVectorTest`, on every target), the **oracle**
(`npm run check`, whose `vkCommit`, link and device-link derivations apply the floor), and, since
2026-11-16, the **web** client:

- **Web** (`web/`, vitest), in `web/src/crypto/trust/keyfloor.vectors.test.ts`, which reads the file
  through `vector("keyfloor.json")` of `web/src/crypto/trust/vectors.ts`. The row it owns is
  `vaultlog.vkCommit`: `vkCommit` in `web/src/crypto/trust/vaultlog.ts` throws on an all-zero `vk`
  before `hkdfSha256` is called, and `keyMatches` answers `false` for an all-zero `vk` without calling
  it. The web client handles no links (design §13), so the `links.derive` and `devicelink.derive` rows
  are another client's: the suite names them as such, one by one, and fails on a row of an operation
  it does not know.

One runner does **not** grade it yet:

- **Extension** (`extension/`, `node --test`). It verifies no vault logs and handles no links, so it
  has no function behind any of the three operations, and all three rows are another client's. Its
  harness reads `../../spec/test-vectors/keyfloor.json` as `extension/src/crypto.vectors.test.ts`
  reads its files, and names the three rows as another client's. Rule 4 still binds its own key
  paths (an envelope sealed or opened under a zero key, an HKDF input key of zeros in `hkdfSha256`
  of `extension/src/crypto.ts`); this file has no rows for those yet.

### The version-3 assisted-recovery rows

A review of operator-assisted recovery (2026-11-16) changed it: a recovery copy names its account's
address, `recovery-cli assist` compares it with the address the operator types, the answer names the
address and carries a commit value that a reset must present, and an answer travels as a one-line
token that says which request it is for. `escrow-v3.json`, `recovery-v3.json` and
`answer-reader.json` pin those forms. They were written by the oracle from the specification text of
2026-11-16 alone (the text before that day's corrections), before any implementation of it was
read, and they are **new files**: the old forms stay in `escrow-v2.json` and `recovery.json`,
untouched, for the readers that still need them (spec 04 §3).

Who grades them:

- **The oracle**: `npm run check` regenerates the three files byte for byte and recomputes every
  row (`src/versioned.mjs`, `src/recoverycopy.mjs`, `src/answer3.mjs`, `src/answerreader.mjs`,
  `src/assist.mjs`).
- **Kotlin**, by layer (spec 04 §4 "Two layers" and "Who reads what a person typed"): core
  `crypto/EscrowV3VectorTest` grades the statement forms (`Escrow.sealUvkV3`'s frames), the shared
  check of the tools' whole check (`Escrow.openForAssist`, `Escrow.openForFleet`) against `open`'s
  `expectShared` where a row has it and `expect` elsewhere, and the shared opener (`Escrow.open`)
  against `expectOpener`; it leaves out the rows its inputs cannot carry (an argument the operator left
  out, both anchors given, the fleet dump's fingerprint column, a copy that is not canonical
  base64url). `recovery-cli`'s `AssistV3VectorTest` grades the tool: every `open` row as the operator
  types it (`assist`'s argument reading and the typed lines, the fleet `verify` through
  `EscrowVerify`), and every `assist` row through the whole run (`runAssist`: the command line, the
  clock where the tool checks it, the identity file's bytes, the typed seed and lines, the token it
  prints). Core `trust/RecoveryV3VectorTest` grades the answer's form, its commit hash, its sizes, the
  device (`AssistedRecovery.openV3`), `commitCheck`'s string rows and the worked example; core
  `trust/AnswerReaderVectorTest` grades the shared reader (`AnswerToken.read`, `readFile`). A row the
  code answers otherwise is a finding: it is left out of the graded test under its finding's name, so
  the build stays green; the rows of findings since fixed are graded again, each also by a test named
  after its finding. None is open.

  (`openEscrow`) against every `expectOpener`; in `recovery-v3.json` `answers`, `sizes`, `commitHash`,
  the device's `open` and `workedExample`; in `answer-reader.json` that its token is
  `recovery-v3.json`'s answer for alice. It names the rows that are another client's, one by one:

  command line is strict, so the web answers `expectOpener`, never `expect`, for a grouped anchor or
  an acknowledgment with white space around it. The extension handles none of this.

  null, number and object rows, which the server answers only for a stored request past its hold and
  an operator's session (a test needs the server suite's request fixture).

Every fixed value is named in each file's `_about` (the first bytes of
`SHA-256("andvari-vector-oracle|" + label)`, as everywhere in the oracle's files), so any row can be
recomputed by anyone.

**Changed with the specification's corrections of 2026-11-16**, which settled the twenty places the
first text left open: the `pending` table is gone, its six rows settled and moved into `open` (a
pre-signed copy is `unknown_format` for the tools; the tool removes spaces, tabs and dashes from a
typed anchor, case kept, while the shared opener takes only lowercase hex; one order for step 0; a
plaintext under four bytes is `unknown_format`); new `open` rows for both anchors given, the fleet
`verify` that asks for nothing, the trimmed acknowledgment, the order of step 0 before step 2, and
every `assist` refusal by name; `expectOpener` (the shared opener); `commitCheck` and `fulfil` rows
for absent, null and non-string fields and the listed order; the device's frame verdicts in spec 01's
order; and in `answer-reader.json` a wrapped line may hold `:` (the rows wrapped at 80 and 148 are
now read), `answer_bare` needs at least 100 characters (one word and a commit hash alone are now
`not_an_answer`), and a file's bytes are read as UTF-8 (the `readFile` table). Rows that pin the text although a client may not expect it say so
in their `why` (an answer for another address of another length reads as cut short or too long).

**Changed after the code was compared with these rows** (the comparison found four faults in the code,
since fixed, and two places where the text did not say which layer reads what a person typed, since
written in spec 04 §4 "Who reads what a person typed", "Files", "Every refusal has a name" and
"Reading the identity file", and §7 steps 3.0 to 3.2): in `escrow-v3.json`, `expectShared` on the five
`open` rows where the shared check answers otherwise than the command line, and `expectOpener` on the
two acknowledgment rows (the opener compares exactly); `identityFiles` entries carry the `userId` of
their download, and one has an `identityPub` of 31 bytes; new `open` rows for the identity file's key
(`identity_check_failed` at step 0, after the inputs), an acknowledgment followed by a form feed, and
the fleet dump's own refusals; and the `assist` table is read through the whole command line
(`extraArgs`), the identity file's own bytes (`identityFileB64`) and the typed seed (`seedTyped`), with
the clock checked before anything is read, and has 31 new rows: a row for every refusal the text names
(`unknown_option`, `legacy_refused`, `more_than_one_copy`, `bad_copy`, `bad_identity_file`,
`identity_file_mismatch`, `identity_check_failed`, `bad_seed`, a flag given last with no value) with
their order against the seed, the request code and the clock, and rows for how a typed request code
(spaces, tabs and dashes removed, letters without regard to case; a line feed, a carriage return or a
no-break space is no match) and a typed confirmation (only space and tab removed from its ends) are
read. `recovery-v3.json` and `answer-reader.json` did not change. Two choices of the oracle where the
text is silent: a download's fields other than its four are passed over (no row's verdict depends on
it), and the fleet check reads a dump row's `fingerprint` column as the recovery key its copy is
sealed to, so one that is not this sheet's is `recovery_fp_mismatch`, the name the tool gives it (the
row `verify-dump-names-another-recovery-key` rests on this reading).

### The `emailNorm` rows

The address rule of spec 01 §5.5 and design §2.3 lives in one place, the `emailNorm` section of
`encodings.json`: **127 rows**, 45 accepted and 82 refused. A row is
`{ "why": text, "input": the address as typed, "expect": { "verdict": "ok", "emailNorm": text } }` or
`{ "why", "input", "expect": { "verdict": "invalid_email" } }` (on the wire, `400 invalid_email`;
no `emailNorm` key). Rows 0–35 pin the strip, the ASCII-only lowercasing, the byte range, the
3–254-octet length after the strip and the single `@`; rows 36–126 (2026-11-15) pin the
dot-atom local part (1 to 64 characters of `a–z`, `0–9` and ``!#$%&'*+/=?^_`{|}~-``, single dots
between non-empty parts), the domain under the `origin` host grammar (two or more labels of 1–63
characters, no trailing dot, a last label neither all digits nor `0x` plus hex), and the forms a mail
library would rewrite to another mailbox (angle brackets, comments, quotes, display names, groups, two
addresses). Every refusal is the one verdict `invalid_email`, so no row depends on which check fires
first. Row 5 (`a@b`) was accepted before the domain rule and is refused now.

Who grades them: **core** on every target, the **web twin**, the **CLI** and the **server** (whose
`emailNorm` decides `400 invalid_email` wherever an address is taken) grade all 127 rows. Design §17
names only the `origin` rows of `encodings.json` for the **extension**; an extension twin that
computes `emailNorm` itself grades all 127 rows too.

Every other file whose grammar takes an address requires it to be its own `emailNorm`, and each has a
row with an address that passes the strip, the case, the byte range and the single `@` but is not a
dot-atom (`alice<alice@example.com>` or `carol<carol@example.com>`): `statement-v2.json`
(`email_b64n`, `non_canonical`), `links.json` (an enrol offer's `email`, `non_canonical`),
`devicelink.json` (`outer.email`, `bad_outer`; the bundle's `email`, `bad_bundle`),
`recoverykit.json` (the kit's `E`, `bad_kit`) and `signup.json` (`pow`, `400 invalid_email`). Every
address those files carry where it must already be normal, outside the refusal rows, is its own
`emailNorm`, and every address typed into `signup.json` (`email`, `registerEmail`) outside the new
row normalises to one. `enrolllink.json`
is the v1 enroll link, which carries its address verbatim and is on design §15's deletion list; its
non-ASCII addresses are not under this rule and were not touched.

## Rules

1. **Never edit a vector to make a failing test pass.** A red vector means an engine
   diverged; fix the engine, or change the spec first and then the vector.
2. **Generated files are rewritten wholesale** by `tools/vector-gen` — hand edits to them
   are lost on the next run, silently.
3. **Adding a vector** means adding its consumer in *every* engine that the behaviour
   touches, in the same change. A file only one engine reads is not a shared vector.
4. **The "consuming suites" column is derived, not remembered.** It is regenerated from a
   grep of each basename across `core/src`, `web/src` and `extension/src` (test files only);
   audit H114 found it naming suites that did not exist and omitting one that did, because
   it had been written from memory. The opt-in `web/src/crypto/noble-extension-poc.test.ts`
   also reads `kdf.json` but is skipped in every default gate, so it is not listed as a
   consumer of anything. `scripts/verify.sh` deliberately states no file counts of its own
   and points here (audit H115) — this file is the single provenance manifest.
5. **Adding a case to a randomized file** (`seal`, `secretstream`, `sharedgrant`): regenerate
   to scratch and splice only the new key; the committed seals stay byte-identical.
