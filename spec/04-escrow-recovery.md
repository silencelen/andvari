# andvari spec 04 — escrow & recovery

Recovery exists because zero-knowledge + forgotten master password = data loss. andvari has two
recovery paths:

- **The recovery kit** (§6): mandatory for every account on every instance. A 256-bit secret the
  person keeps; nobody else can use it without their email address, and nobody can recover the account
  without it.
- **Operator recovery** (§1–§5, §7): an explicit opt-in, after a warning, on a **private** instance
  whose operator set up a recovery key. The account's UVK is escrowed to the instance recovery key,
  whose private half exists only offline. Holding that key ⇒ ability to decrypt, and act as, every
  opted-in account (spec 05 R3). **On the public instance there is no operator recovery** (variant
  R, decided on 2026-11-15): the kit is the only way back, and losing the master password and the kit
  loses the account. Appendix A of spec 03 lists what variant K would change.

## 1. Instance recovery keypair

- X25519 via `crypto_box_seed_keypair(seed)`, `seed` = 32 random bytes generated by
  `tools/recovery-cli keygen` on an **offline machine** — never the server, and never any always-on
  host that administers it. The same seed yields the **recovery-key signing key**
  `crypto_sign_seed_keypair(seed)` (spec 01 §5.5), which signs rotation statements (§5) and
  assisted-recovery payloads (§7); verifiers require `ed25519_pk_to_curve25519(signerPub)` to equal
  the recovery public key that the pinned card's `recoveryFp` names.
- **Fingerprint** `recoveryFp` = lowercase hex SHA-256 of the 32-byte public key; the **short form**
  is its first **32 hex chars (128 bits)**, grouped in 4s.
- The instance card carries `recoveryFp` (spec 01 §5.2), or `none` when the instance offers no
  operator recovery. `andvari setup` offers the key ceremony only on a private instance with mail
  configured (assisted recovery needs the emailed code); without it, and on a public instance under
  variant R, `recoveryFp = none`.
- **Recovery sheet** (printed ×2 + one USB copy, stored separately — safe / fire box): seed as
  base64url AND as a QR code, pubkey base64url, full fingerprint, generation date, and the one-liner
  ("run `recovery-cli assist` and follow prompts"). The operator account's own recovery kit is printed
  twice and stored with it.
- The private seed MUST NEVER exist in: git, any backup system, any object store or cloud, the server,
  or the disk of any always-on machine. `recovery-cli` holds it in memory only during a ceremony.
- Server env pins `ANDVARI_RECOVERY_PUBKEY` and `ANDVARI_RECOVERY_FINGERPRINT`. The server checks at
  load that the fingerprint is the SHA-256 of the pubkey and REFUSES TO START otherwise; an instance
  with neither is unconfigured and starts with operator recovery off.

## 2. Pinning and consent (defense against key substitution)

**The anchor is the card.** The recovery key a client seals to is the one the **pinned instance card**
names (`recoveryFp`, spec 01 §5.2–§5.3), never a value the server serves on its own and never a
fingerprint a human types. The served key (`GET /recovery-pubkey`, spec 03 §17.4) must hash to that
`recoveryFp` at full length.

**Consent lives with the account, not the server.** The person's choice is recorded in UVK-sealed
account state (spec 02 §9) as `recovery = {posture: "private" | "operator", fp, at}`, mirrored in
device state. It is written only by an explicit choice: at sign-up, in Settings, or on re-consent. The
server's `users.recovery` is a mirror for its own route checks; **clients never decide anything from a
served posture.**

A client seals an escrow blob (§3) only when **all** of these hold:

1. its account-state record says `operator`;
2. the pinned card's `recoveryFp` equals the consented `fp`, or follows from it by a chain of valid
   rotation statements (§5);
3. the served recovery public key hashes to that `recoveryFp` at full length;
4. its **own device-state mirror** of the recovery record agrees (below);
5. the pinned card's `kind` is not `public` (variant R, below).

No human types a fingerprint, and no served value can turn a private account into an escrowed one.

**First consent.** When a person turns operator recovery on, at sign-up or later in Settings, the
client first walks the served card chain **from card 0** to the newest card, whatever its pin root.
Every change of `recoveryFp` along it must be matched by a stored 0x08 rotation (§5) from the old value
to the new one, or by a chain of them that leads from the old value to the new one (a card may jump
from A to C while the served rotations go A to B and B to C). If any change is not, the choice shows
the unsigned-change warning (§5) and preselects "Only me".

- What anchors card 0, per pin root: baked — `PUBLIC_INSTANCE.card0Hash`; kit — the kit's
  `card0Hash`; setup — this device signed card 0; link offer — the offer's `cardHash`, which the
  creator's device verified and which fixes every earlier card through `prev`; enrol and Trust Gate —
  nothing beyond the chain the server served at first use.
- What the walk cannot detect: an enrol or Trust Gate pin made on a server that was **already**
  compromised, which can serve a chain fabricated from card 0 naming its own recovery key from the
  start (spec 05 R22). Everyone whose card 0 is anchored before the swap is warned.
- A server whose operator really lost the old seed shows this warning to every later opt-in, for good;
  the copy says to ask the operator why.

**Own mirror.** A device seals an escrow, or re-seals one after a rotation, **without asking** only when
its own device-state mirror of the recovery record agrees with the account-state record. The mirror is
set on a device only by the person's own choice made there (sign-up, Settings, re-consent) or by a
verified re-seal made there. **A device link does not carry it**: a linked device asks once, like a
password-only one (the bundle's account-state checkpoint only refuses rollbacks). A device without a
mirror seals nothing on its own; when a seal is due it asks "Your account lets the operator of *name*
(*origin*) restore it. Keep that?" with [Not now] (the default: nothing is sealed, and it asks again at
the next unlock), [Keep operator recovery] and [Turn it off]. Both choices need the master password
(`PUT /account/recovery`, spec 03 §3.1), and then the mirror is set. Without this rule a server could
serve a password-only device an old account state whose record still says `operator` and, with a
rotation signed by whoever holds the seed, make that device re-seal unasked.

**Variant R (the public instance).** When the pinned card's `kind` is `public`, a client never shows
the operator choice or "Ask the operator", never seals or re-seals an escrow, and ignores
`recoveryFp`, whatever the card or the account state says. The rule is compiled into every client, so a
stolen operator key cannot turn escrow back on with a new card; a `kind` change needs the Trust Gate,
and store builds never follow one for the baked public instance (spec 01 §5.2). The extension never
seals or re-seals an escrow on any instance (spec 01 §6.5).

**The operator account** is never offered operator recovery: it would be circular.

**Names in recovery copy.** `{instance name}` is the pinned card's `name` and `{origin}` its origin,
both signed by the operator's key and rendered as plain text. Recovery copy never shows a name the
server reports for an account, such as the operator account's display name.

**Exact copy** (normative; all clients use the same strings, pinned by tests). On a private instance
with a `recoveryFp`:

> **How should this account be recovered if you forget your master password?**
>
> ◉ **Only me** *(selected)* — You'll save a recovery kit now. If you lose both your master password
> and your recovery kit, nobody can get your vault back, not even the people who run this server.
>
> ○ **Me, or the person who runs {instance name}** — They can restore your account if you forget your
> master password.

Choosing the second option shows, before anything changes:

> **Let the person who runs {instance name} ({origin}) restore your account?** — With this on, they
> keep a key that can restore your account. Restoring it means they could open your vault, every
> password, note and card in it, and act as you. Anyone who gets into your email can ask them to reset
> your account; a request waits 7 days, and your signed-in devices can cancel it. Choose this only if
> you trust the person who runs this server with your passwords. You will still get your own recovery
> kit.
>
> ☐ I understand that the person who runs this server could open my vault and act as me.

When `recoveryFp` is `none` the second option is not shown at all. On a public instance (variant R)
sign-up shows no choice, only "You'll save a recovery kit now. If you lose both your master password
and your recovery kit, nobody can get your vault back." Turning operator recovery off later shows:
"This deletes the operator's recovery copy from the server. It cannot undo a copy the operator may
already have made."

## 3. Escrow blob

`sealed = crypto_box_seal(recoveryPub, SignedStatement)` — the spec 01 §5.1 frame with purpose code
`0x02` (`escrow-uvk`), signed with the account's joint Ed25519 key (spec 01 §5). **A recovery copy
says whose it is** (rule of 2026-11-16): its statement, version 3, carries the account's
address, inside what the account's own key signs:

```json
{"v":3,"purpose":"escrow-uvk","userId":"<uuid>","email":"<email_b64>","identityKey":"<b64_32 seed-derived X25519 identityPub>","recoveryFp":"<hex64>","issuedAt":<ms>,"key":"<b64_32 UVK>"}
```

- **`email`** is of type `email_b64` (spec 01 §5.1): the unpadded base64url of the ASCII bytes of the
  account's `emailNorm` (spec 01 §5.5), decoded 3..254 bytes, re-encoding identically, and already
  normal (`emailNorm` of the decoded text equals it exactly). It is the `email_b64n` grammar without
  the literal `none`. The sealing client writes the address the account was registered with: the
  `emailNorm` it sent at registration, or, on a later seal, the `emailNorm` of the session it is
  signed in with (an account's address never changes: no route changes it). A client never takes the
  address from a server answer on its own.
- Keys appear in exactly the order shown; the statement is at most 1,024 bytes (spec 01 §5.1), which
  the longest address (254 octets, 339 characters of base64url) keeps it under.
- The sealing client MUST meet §2's conditions; `recoveryFp` is the pinned card's, and
  `hex(SHA-256(recoveryPub)) == recoveryFp` IN FULL (64 hex). The signer key MUST map to `identityKey`.
- **Every seal is version 3**: at registration (`recovery.escrow`), on `PUT /account/recovery` (turning
  operator recovery on) and at a re-seal after a signed rotation (`PUT /escrow/self`). A client that
  cannot name the address seals nothing.
- The opened plaintext must start with the four bytes `avs\x02` (`unknown_format` otherwise).
- **The old form.** The version-2 statement of the same purpose has the same keys without `email`:
  `{"v":2,"purpose":"escrow-uvk","userId":<uuid>,"identityKey":<b64_32>,"recoveryFp":<hex64>,"issuedAt":<ms>,"key":<b64_32>}`.
  It does not say whose copy it is, so `recovery-cli assist` and the fleet `verify` refuse it after
  opening (`no_address`, §4); no client seals it. The owner chose a clean break: no account is carried
  over, and an account whose copy is of the old form seals a new one (turn operator recovery off and
  on again). The shared opener still reads it, for `spec/test-vectors/escrow-v2.json` and the released
  tool's `recover` only, and likewise the pre-signed JSON form, which
  does not start with the magic and which the tools refuse unread at §4 step 4 (`unknown_format`).
- Uploaded at registration (`recovery.escrow`, spec 03 §14.3) or on `PUT /account/recovery`, and
  re-uploaded only after a signed rotation (`PUT /escrow/self`, spec 03 §3.2). UVK stability (spec 01
  §4) keeps blobs valid across password changes. Test vectors: `spec/test-vectors/escrow-v2.json`
  (the old form); the version-3 form's vectors are added in files of their own.
- **No copy is retained.** A replaced or deleted blob is gone. Every path that destroys or replaces key
  material (an escrow change, a re-seal, a password change, a kit or assisted recovery, a kit rotation,
  a vault purge, an account deletion) runs with `PRAGMA secure_delete=ON` and is followed by
  `PRAGMA wal_checkpoint(TRUNCATE)`, so old bytes are not carvable from the live file or its WAL.
  **Backups taken before a change still hold the old blob**: the response to a stolen recovery sheet
  includes rotating those backups out.

## 4. Operator flows

**What operator recovery gives the operator.** The escrow yields the UVK, the UVK opens the identity
seed, and the seed is the account's signing key. An operator who restores, or simply opens, an
opted-in account's escrow can read that person's vaults, **act as that person** (sign log entries,
write account state), and read every shared vault the person belongs to. The access is permanent: no
account re-key exists (spec 05 R33).

**Escrow ⊥ vault lifecycle.** Escrow seals the UVK only — no VKs, no items. An assisted recovery
rewrites the verifier, `wrappedUvk` and KDF settings and touches neither grants nor the vault logs, so a
recovered account keeps every membership and ownership. A lost owner is recovered (kit or operator),
then signs in and hands over or deletes its vaults with signed log entries. No server route reassigns
an owner.

**Account deletion ends both recovery paths** (spec 03 §13): the `escrow` and `member_recovery` rows go
in the deletion transaction. The deletion is refused while the account owns a vault other accounts
still use, so succession is not lost by it.

**Genesis ceremony (before the first opt-in):**

1. Offline machine → `recovery-cli keygen` → sheet ×2 + USB; verify both printouts scan back to the
   same seed.
2. Pin pubkey + fingerprint into the server env (`andvari setup` does it, §1); card 0 then carries
   `recoveryFp`.
3. **Canary check:** `recovery-cli canary make <pubkeyB64>` seals the FIXED canary payload
   `{"v":1,"userId":"00000000-0000-0000-0000-000000000000","keyType":"canary","key":"<base64url of 32×0x5A>","sha256":"<of that>"}`
   to the pinned pubkey; store the sealed canary beside the sheet. Then, from the printed sheet ONLY
   (re-typed/scanned, not from the generating session), `recovery-cli canary verify <sealedB64>` must
   open it. Proves print → restore → unseal end-to-end before anything real depends on it. (The canary
   is not an escrow and keeps its own fixed format.)

**Reading an escrow.** `POST /admin/accounts/{userId}/escrow { currentAuthKey }` (spec 03 §18.6)
answers `{ userId, sealed, encryptedIdentitySeed, identityPub }`: the blob plus the account's identity
file, all server-supplied and used only as something to check against. It emails the person "the
operator downloaded your recovery copy" and is audited. It is the first step of an assisted recovery
(§7), never a recovery on its own.

**Opening an escrow offline** (`recovery-cli assist`, and the fleet `verify`) runs these steps IN
ORDER; the first failure aborts with its verdict.

**Two layers.** The **shared opener** (core `Escrow.open`, and the web
twin) is a parser and verifier of the copy: steps 0 to 6 below without `--email`, answering what it
opened and in which form (version 3 with its address, version 2, or the pre-signed form). The
**tool's whole check** is steps 0 to 8: the tools (`assist`, `verify`) refuse at step 4 anything that
does not start with the magic, refuse at step 7 a form that is not version 3, and `assist` compares the
address at step 8. Core gives the tool's whole check as `Escrow.openForAssist` (steps 0 to 8) and the
fleet check as `Escrow.openForFleet` (steps 0 to 7, unanchored, no `--email`), so the two tools and the
web twin cannot differ. `escrow-v2.json` grades the shared opener; the version-3 vectors' `open` rows
grade the tool's whole check.

**Who reads what a person typed.** Reading human input is the
**command line's** job, and the shared check is strict. The command line removes spaces, tabs and
dashes from a typed anchor (step 0.2); removes space and tab, and nothing else, from both ends of a
typed confirmation (steps 2 and 9); and reads the request code by removing spaces, tabs and dashes and
comparing its letters without regard to case (§7 step 3.2). It hands `Escrow.openForAssist` and
`Escrow.openForFleet` values already in their grammar, and they refuse anything else: an anchor that is
not 32 to 64 lowercase hex is `bad_anchor`, an acknowledgment that is not exactly the sentence is
`unanchored_not_acknowledged`. A client without a command line (the web's twin) is strict. So a
grouped anchor, or a confirmation with white space around it, is "ok" from the tool and the refusal
from the shared check. "White space" here is space (U+0020) and tab (U+0009) only, not the platform's
wider notion. Every other argument is checked **exactly as given**, nothing removed, before anything is
read or asked, and the value checked is the value used: an id, a key or a copy with white space around
it is refused by its name.

**Files** (the identity file, and the fleet check's seed file and dump) are decoded as strict UTF-8:
any byte sequence that is not valid UTF-8 is refused, nothing is replaced. Every field of the identity
file is checked against its grammar before it is used or shown (`userId` a lowercase uuid,
`encryptedIdentitySeed` and `sealed` canonical base64url, `identityPub` 32 bytes), and the tool prints
none of them; everything the tool prints, on every path and before the seed is asked for too, goes
through one escaping function that makes control characters, line and paragraph separators and
direction overrides visible, so that nothing a file holds can disguise what the operator reads.

**Every refusal has a name**, the one the tool prints as `REFUSED (<name>)`. Besides the verdicts of
the steps below and of §7 step 3, the command line's own: `unknown_option` (an option the command does
not have), `legacy_refused` (the old `--legacy` switch), `more_than_one_copy` (more than one copy given
on the command line), `bad_copy` (a copy, given or downloaded, that is not canonical unpadded base64url
exactly as given), `bad_identity_file` (an identity file that cannot be read, is not UTF-8, or is not a
recovery-copy download), `identity_file_mismatch` (a download for another account than `--user`),
`bad_seed` (a typed seed that is not 32 bytes of base64url, step 1), the fleet check's `canary_failed`
(the canary row does not open to its fixed payload with the sheet given), and `unexpected_fault`: anything
unexpected after the arguments are accepted ends as this one line, which names the kind of fault (the
exception's class, never its message) and the stage, never a secret, with a non-zero exit and nothing
produced. The tool never ends in a stack trace. A flag given last with no value is an absent argument,
named by its own check. An option given more than once, with the same value or another, is
`repeated_option`, decided while the command line is read (with `unknown_option`), never taken as its
last value; this holds for every command. `rotate`'s own: `unknown_option`, `repeated_option`,
`bad_instance` (`--instance` absent or not a lowercase uuid), `bad_key` (`--to` absent or not a 32-byte
key in canonical base64url exactly as given), `bad_seed`, `same_key` (the new key is the outgoing one),
`unexpected_fault`. `canary verify`'s: `bad_copy`, `bad_seed`, `canary_failed` (the canary does not
open to its fixed payload with this sheet); `canary make` and `fingerprint`: `bad_key`; a `canary`
subcommand it does not have: `unknown_option`. The fleet `verify`: `missing_argument` (a file not
named), `bad_seed`, `bad_dump`, `unknown_option`, `repeated_option`, `instance_file_missing`
(`--outgoing-sheets` without `--instance-file`), `wrong_sheet` (with `--outgoing-sheets`, a seed file
that is not the current sheet, or a pasted seed that is not the outgoing sheet asked for), and
`--instance-file`'s refusals (§5). `--instance-file`'s own, for `assist` and the fleet `verify` alike,
decided while the command line is read: `card0_hash_required` (the file without `--card0-hash` or
`--instance-file-unchecked`), `bad_card0_hash` (a value that is not 64 lowercase hex once spaces and
tabs are removed, or both options given), `instance_file_missing` (either option without the file);
and when the file is read, `card0_mismatch` (§5). A server address anywhere on the command line:
`server_url_refused`, before anything else.

**The tool's inputs are hostile.** Every file the tool reads is read only up to
its limit, and one over it is refused by that file's name without being read whole: the identity file
1 MiB (`bad_identity_file`), the instance file 4 MiB (`bad_instance_file`), the fleet check's dump
64 MiB (`bad_dump`), its seed file 4 KiB (`bad_seed`). The three JSON files (identity file, instance
file, dump) are refused, by the same names, when an object in them gives a key twice (keys compared
after their escapes are decoded, so `"a"` and `"a"` are one key; a parser would otherwise keep
the last one silently) or they nest deeper than 32 levels; the instance file also when it carries more
than 4,096 cards or 64 rotations. A line typed or piped on standard input (a seed, a confirmation) is
read to its end but kept only to 4,097 characters, so an overlong line fails the grammar of what was
asked (`bad_seed`, `not_confirmed`, `unanchored_not_acknowledged`) and is never held whole; a seed
typed at a terminal with echo off is read by the platform's console, which a person drives. A
command-line argument is bounded by the operating system. Nothing the tool reads ends in a stack trace
or an out-of-memory error: the limits come before the reading, and anything else ends as the one
`unexpected_fault` line.

0. **inputs, before the seed is asked for, in this order** (written here once):
   1. `--user`: absent, or not a lowercase uuid, is `bad_user_id`;
   2. the anchor: `--identity-fp` absent without `--no-identity-anchor`, both given together, or a
      value that is not 32 to 64 lowercase hex, is `bad_anchor`. The **command line** removes spaces,
      tabs and dashes from what was typed (a fingerprint is printed in groups) before it hands the
      value on; it does not change case, so an upper-case letter is `bad_anchor`. The shared opener
      (`Escrow.open`, `openForAssist`, `openForFleet`) takes only 32 to 64 lowercase hex and refuses
      anything else (`bad_anchor`), which is what `escrow-v2.json`'s row "anchor with separators" pins;
   3. `--identity-file` absent: `identity_check_required`. The shared openers decide this here, at step
      0, before they look at the acknowledgment of step 2;
   4. for `assist`, **`--email`**: the address of the person the operator is helping, which the
      operator types from their own knowledge of that person, never from the console or anything else
      the server showed. Absent, or with no `emailNorm` (spec 01 §5.5): `bad_email`. The tool keeps
      `emailNorm(--email)`;
   5. for `assist`, a copy given on the command line in place of the download's: not canonical
      unpadded base64url exactly as given, `bad_copy`.

   The shared openers, given the identity file, then require its `identityPub` to be 32 bytes
   (`identity_check_failed`), still at step 0. `assist`'s own three request arguments are checked
   before this step (§7 step 3.1), and its request code and the clock after it (§7 step 3.2); the
   identity file is read and the seed asked for only after these.

   **Reading the identity file** (before the seed is asked for): it cannot be read, is not strict
   UTF-8, or is not a recovery-copy download `{userId, sealed, encryptedIdentitySeed, identityPub}`:
   `bad_identity_file`. A download is the four fields the server sends; a file with other fields
   beside them is still a download, and the others are ignored. When a copy is given on the command
   line in place of the download's, only the copy that is opened is checked: the download's own
   `sealed` is then not read at all, and may be absent; its `userId` is not `--user`: `identity_file_mismatch`; its `identityPub` is
   not 32 bytes of canonical base64url: `identity_check_failed`; the copy it carries (or the one given
   in its place) is not canonical unpadded base64url: `bad_copy`;
1. read the sheet seed, derive the recovery keypair, print its fingerprint grouped. A typed seed is read
   like everything else a person types: space and tab are removed from both ends and nothing else, and
   what remains must be exactly 32 bytes in canonical unpadded base64url (`bad_seed`): padding, the
   other base64 alphabet (`+`, `/`), a no-break space or any other character is `bad_seed`. A seed
   file (the fleet check's) is one line: its line ending, LF or CR LF, is removed, then the same rule;
2. **anchor**: `hex(SHA-256(identityFile.identityPub))` starts with `--identity-fp`
   (`identity_fp_mismatch`). The fingerprint MUST come from outside the server: the person's **account
   ID** read out by the person from their own kit (the better source) or from a notice **older than
   the request** (this server sent the emails, and the request's own mails are its word about the
   request), or the operator's or a co-member's own pin of them. A value the console or `andvari-cli`
   displays is the server's and is never an anchor (rule of 2026-11-16: nothing the server says is
   offered as something to check against). For a person with
   neither a kit nor an older notice there is no anchor from outside the server: the comparison is void,
   and the operator's own knowledge of the person is the only check. Unanchored mode instead requires the operator to
   type `I understand this recovery is UNANCHORED` (`unanchored_not_acknowledged`), checked here, after
   every input of step 0. Every typed confirmation (this one and step 9's) has space and tab, and only
   those, removed from both ends by the **command line**, and is then compared exactly; the shared openers compare the value they are given exactly and remove nothing. The fleet `verify` asks for nothing: it recovers nothing and prints no key,
   runs unanchored by design, supplies this acknowledgment itself, and says in its output that its
   check is unanchored and what that means. **Unanchored**, "the anchored identity key"
   in steps 5 and 6 is the identity file's own `identityPub`: steps 5 and 6 still bind the copy to the
   file, and nothing binds the file to the person, which is the stated residual below;
3. `crypto_box_seal_open` (`unopenable`);
4. format: the opened plaintext must start with the four bytes `avs\x02`, or it is `unknown_format`;
   a plaintext shorter than four bytes is `unknown_format` too, decided here before spec 01 §5.1's
   frame rules (whose `bad_frame` for a frame under four bytes applies where no owning section checks
   the magic first). The tools read nothing of a plaintext that fails this step, the
   pre-signed JSON form included; `assist` and `verify` then say: "This recovery copy is
   damaged, or was sealed before recovery copies were signed, and cannot be used. If the person can
   still sign in on some device, they can seal a new copy there by turning operator recovery off and
   on again, and you download the copy again. If they cannot sign in anywhere, the operator cannot
   recover this account." (Turning operator recovery off and on needs the master password, which a
   locked-out person has lost.)
   The shared opener's reading of the pre-signed form stays for the released tool's `recover` and the
   old vectors only;
5. frame, purpose `0x02`, strict parse (`bad_frame`, `non_canonical`, `bad_statement`); the
   statement's `userId == --user` (`user_mismatch`) and `recoveryFp == SHA-256(recovery pub)`
   (`recovery_fp_mismatch`); the signer maps to the ANCHORED identity key (`signer_not_pinned_key`);
   the signature (`bad_signature`); and after it, the statement's `userId`, `identityKey` and
   `recoveryFp` EQUAL the anchor (`identity_mismatch`). The reader tries both templates of 0x02: the
   key set picks one (a statement with `email` is matched against the version-3 template, one without
   against the version-2 template), and a statement that is not canonical under the one it picked is
   `non_canonical`. Then step 6 of spec 01 §5.1 requires each template's own `v` (3 and 2), so a
   version-2 key set marked 3 and a version-3 key set marked 2 are both `bad_statement`.
   This opener accepts both versions; step 7 is where the tools refuse the old one;
6. **identity check**: open `encryptedIdentitySeed` under the escrowed key with `Ad.idkey(--user)`,
   derive the X25519 public key, require it `==` the anchored identity (`identity_check_failed`);
7. **the copy says whose it is** (the tools only): a copy whose statement is version 2 is refused
   `no_address`, and the tool says: "This recovery copy does not say whose it is, so it cannot be
   checked against the person you are helping and cannot be used. If the person can still sign in on
   some device, they can seal a new copy there by turning operator recovery off and on again, and you
   download the copy again. If they cannot sign in anywhere, the operator cannot recover this
   account." (Turning operator recovery off and on needs the master password, so a person who has
   lost it and has no signed-in device cannot replace the copy);
8. **the address**: the statement's `email`, decoded, must equal `emailNorm(--email)` byte for byte
   (`email_mismatch`). The tool then says whose copy it is, in the account's own signed words: "This
   recovery copy is <decoded email>'s, not <typed address>'s. Do not continue: the server gave you
   another account's copy." The fleet `verify` has no `--email` and skips this step;
9. print the account, **the address the copy names** (decoded, marked as signed by the account), the
   identity fingerprint (32 hex grouped) and `anchored: yes/no`, and require the operator to type
   `RECOVER <first 8 characters of the userId>` (space and tab removed from both ends, then compared
   exactly; anything else is `not_confirmed` and nothing is produced). The fleet `verify` stops after
   step 7 and prints a line per account; a row of its dump without the identity columns is
   `identity_check_required` (step 0.3), with the sentence that says how to re-export the dump.
   **One dump row, in this order, the same for every row:** the row's `fingerprint` column, when it
   is present, against the keys of the sheets given (the seed file's, and with `--outgoing-sheets`
   each outgoing sheet pasted): a column naming one of them picks the sheet that opens the copy; a
   column naming an outgoing key whose sheet the operator said is no longer held is
   `outgoing_sheet_gone`; with `--instance-file`, a column naming the current key or an outgoing key
   the rotations prove, whose sheet was not given, is `SKIP`, **not checked** (see "Which key each
   copy is sealed to"); any other column is `recovery_fp_mismatch`. Then the copy's grammar (`sealed` canonical unpadded base64url exactly as
   given, `bad_copy`); for the canary row only, the canary's own opener (`canary_failed`); the
   identity columns (`identity_check_required`); then steps 0 to 7 above.

The UVK never touches the online machine. **What the typed address and the anchor each do.** The
address (steps 0 and 8) stops the server from putting another member's copy under a request: the copy
that opens is the one whose own signed statement names the person the operator is helping. The
anchor (step 2) stops a copy of a server-minted identity that claims that person's address. The
**unanchored residual:** `--no-identity-anchor` still refuses another member's copy (steps 5 and 8),
but cannot detect a wholesale server-minted identity; every device that unlocked the account before
refuses that forgery at the next unlock (spec 01 §5 self-identity backstop).

**Annual drill** (calendar it — an instance with no drill has an untested recovery path): `canary
verify` from the printed sheet; a fleet `verify <seedFile> <escrowDumpJson>` pass over every escrowed
account (steps 0–7 above, unanchored, so a copy of the old form FAILs with `no_address`; the dump carries each account's identity columns:
`SELECT e.userId, e.sealed, e.fingerprint, e.updatedAt, u.encryptedIdentitySeed, u.identityPub FROM
escrow e LEFT JOIN users u ON u.userId = e.userId`; after a rotation, with `--instance-file` and the
server's `GET /api/v1/instance` answer, `--card0-hash` and, while any account is on an outgoing key,
`--outgoing-sheets`, see "Which key each copy is sealed to" below; a run that ends in exit 2 has not
checked every copy and is not a passed drill); and a full assisted recovery of a dedicated drill
account on a scratch server (`scripts/recovery-drill.sh` drives it, with kit recovery). A failure is a
P1 incident: a new recovery key with a signed rotation (§5) if the old seed still exists, otherwise an
unsigned change that every opted-in person sees behind the warning.

**Which key each copy is sealed to.** The fleet `verify <seedFile> <dump>
[--instance-file <file> (--card0-hash <64 hex> | --instance-file-unchecked) [--outgoing-sheets]]`
prints, per account, its result, the key its copy is sealed to (the first 32 hex of its fingerprint)
and what that key is, its address and the detail. The key is the dump's `fingerprint` column; it is
proven only for a copy that opened with a sheet given (that copy's own signed statement names the
key), and is otherwise the server's word, which the line says. With the file (read and checked as in
§5, from the first card's hash the operator gives, its instance taken from card 0), a key is the
**current** key, an **outgoing** key the rotations prove, or **unproven**; without the file every key
other than the sheet's is unproven. A row on an unproven key is `recovery_fp_mismatch`.

- **A copy that was not opened is never counted as recoverable.** A row whose
  key is the current or an outgoing key, but whose sheet was not given, is not opened: it is `SKIP`,
  **not checked**, neither a PASS nor a FAIL. A server could otherwise replace any copy with garbage
  and label it with an outgoing key, and every later drill would hide it. After the PASS count, one
  line names how many copies were not checked and why (`N NOT CHECKED (SKIP): <n> sealed, by the
  server's word, to the <current|outgoing> key <fp>, whose sheet was not given. A copy that was not
  opened is not proven recoverable: …`). The verdict never says "all" when any copy was not checked:
  it is `All escrowed accounts in this download (M) are recoverable with this sheet.` (or "these
  sheets") only when every row was opened and none failed; `NOT ALL CHECKED: N of the M copies in this
  download were not opened here, so not every account is proven recoverable; …` when none failed and
  some were not checked; the FAIL line when any failed (with `; and N more NOT CHECKED`). The **exit
  status** tells the three apart: **0** every copy checked and good, **1** a failure (a FAIL row, or a
  refusal before any row), **2** none failed but some not checked.
- **The outgoing sheets, given to the fleet check** (`--outgoing-sheets`, which needs
  `--instance-file`: `instance_file_missing`). They are never given on the command line: after the
  seed file (which must then be the CURRENT sheet, `wrong_sheet`), the tool asks for each outgoing
  sheet at a prompt, newest first, by its fingerprint and "outgoing since", without echo or from
  standard input (`bad_seed`; the key must be that outgoing key, `wrong_sheet`); an empty line says the
  operator no longer holds that sheet. Every refusal of the command line, the instance file, the dump
  and the seed file comes before any sheet is read or asked for: the seed file is read after the dump.
  The copies sealed to an outgoing sheet given are then opened and checked like any other; a copy on an
  outgoing key whose sheet the operator no longer holds is `outgoing_sheet_gone`, a FAIL ("this account
  is NOT recoverable"). So a damaged copy labelled with the outgoing key is not checked without the
  outgoing sheet, and is a FAIL with it.
- Before the verdict, one line: `Accounts still on an outgoing key: N`, naming the outgoing sheets
  those accounts need; it says that an outgoing sheet is no longer needed only when N is 0 and every
  row opened with the current sheet, and otherwise that no outgoing sheet may be destroyed yet. That is
  the line the operator reads before destroying an outgoing sheet, and it says what it rests on:
  `Every copy in this download (M) opened with the current sheet, so none of
  these accounts needs an outgoing sheet any more. That rests on the download: an account the server
  left out of it is not covered. Before you destroy an outgoing sheet, check that M is the number of
  accounts you know have operator recovery on.` A server that drops escrow rows from the dump makes
  the line say 0 for accounts it hid; that can only cost the hidden accounts their recovery, which a
  server that drops their rows can cost them anyway (availability only).

Everything it prints goes through the tool's escaping function.

## 5. Rotating the recovery key; `recovery-cli`

A card that changes `recoveryFp` does **not** by itself cause any re-seal.

**Signed rotation (normal case).** The operator runs `recovery-cli rotate --instance <uuid> --to
<newPub>` offline (`--to` the new recovery public key, base64url); it reads the **outgoing** recovery
seed from its printed sheet. It produces a 0x08 statement (spec 01 §5.1)
`{"v":2,"purpose":"recovery-rotation","instanceId":<uuid>,"fromFp":<hex64>,"toFp":<hex64>,"issuedAt":<ms>}`,
signed by the outgoing seed's signing key. The operator stores it (`PUT /instance/rotation`, spec 03
§17.3), then signs the card with the new `recoveryFp` (spec 03 §17.2). The server serves rotations beside the
card chain.

- A client verifies, in order: the parse; `fromFp` is its current fingerprint
  (`fp_mismatch`); the signer against the key `fromFp` names
  (`ed25519_pk_to_curve25519(signerPub)` hashes to `fromFp`, `signer_not_pinned_key`); the signature
  (`bad_signature`); then the `instanceId` (`instance_mismatch`), and that the last `toFp` of the chain it followed is the card's value; it updates its consent to `toFp` and re-seals at its next unlock — only with its own
  mirror (§2), otherwise it asks.
- The re-seal is `PUT /escrow/self {sealed, fingerprint, rotations}` (spec 03 §3.2), which needs a
  session but no password; `rotations` is the chain from the current escrow's fingerprint to
  `fingerprint`, oldest first, because consent may follow more than one rotation.
- A server compromise cannot forge a rotation: the seed is offline. Vectors:
  `spec/test-vectors/recovery.json`.

**A copy sealed to an outgoing key.** The re-seal waits for the person's next
unlock. Until then the account's recovery copy stays sealed to the outgoing key, while every device,
having followed the signed rotation, takes only an answer signed by the key its pinned card names (§7
step 4). The person who needs assisted recovery is the one who cannot unlock, so their copy is often
of this kind. One sheet is not enough for it: the current sheet does not open the copy (`unopenable`),
and an answer the outgoing sheet signs is refused by every device (`signer_not_pinned_key`). So:

- **The operator keeps the outgoing sheet** until the fleet check (§4, "Annual drill"), given the
  server's `GET /api/v1/instance` answer and the first card's hash, checks every copy (exit 0) and
  reports no account on it, and the number of copies in the download is the number of accounts the
  operator knows have operator recovery on. Only then is the outgoing sheet destroyed. An account the fleet check still shows on the outgoing key needs that sheet to be
  recovered.
- **The two-sheet `assist`.** The operator saves the server's `GET /api/v1/instance` answer
  (`{cards, rotations}`, spec 03 §17.1; unauthenticated) to a file, carries it to the offline machine,
  and adds `--instance-file <that file>` to `assist`, with **`--card0-hash <64 hex>`**, the hash of the
  server's first card, which the operator holds. Without that option `assist` is the one-sheet
  command it always was; its `unopenable` sentence then says that a copy sealed before a rotation needs
  this file and both sheets. With it, in this order, the first failure stopping the tool with nothing
  asked and nothing produced:
  0. **The file is tied to something the operator holds.** The file is the
     server's word: a server can make up a whole card chain under its real instance ID, with a card
     key and recovery keys of its own and rotations they sign, and so make any key "outgoing" or show
     an old key as current. So the tool checks the file's first card against the hash the operator
     gives, before anything else of the chain and before any sheet is asked for. Where an operator
     reads that hash today: `andvari-cli card show` on the operator's device (the line `card0Hash`, and
     the `card0Hash` field with `--json`; from the device's own pin, never a fetch); the desktop app's
     Instance details, labelled "card 0's hash", on the device that signed card 0 (the setup pin) only;
     and the operator's own recovery kit, whose QR text carries it as its fourth field
     (`andvari-kit:2:<O>:<C>:…`, §6.2), while the printed kit does not show it in words. With the file
     and neither `--card0-hash` nor `--instance-file-unchecked`, the tool refuses while the command
     line is read (`card0_hash_required`), with a sentence that says where to read the hash; both
     given, or a value that is not 64 lowercase hex once spaces and tabs are removed, is
     `bad_card0_hash`; either without the file is `instance_file_missing`. When the file is read, a
     first card that does not hash to the value given is `card0_mismatch`, and the sentence never
     prints the file's own hash. **`--instance-file-unchecked`** is the one way on without the hash:
     the tool then checks the file against itself only, and every line it prints about the file
     (what it says before any seed, each prompt that names a sheet from the file, the lines on which
     sheet opened the copy and which signs, each refusal that names a key from the file, and in the
     fleet check every table row, the not-checked line, the outgoing-key line and the verdict) ends
     with `[by --instance-file, NOT checked against anything you hold]`, after two lines that say the
     server could have made up its whole card chain and every rotation in it. The fleet `verify`
     takes the same two options, with the same refusals;
  1. after the identity file is read, and **before any seed is asked for**, the file is read and
     checked: not strict UTF-8, not a JSON object, or `cards` or `rotations` not a list of canonical
     base64url frames: `bad_instance_file` (other fields beside the two lists are ignored; the limits
     of "The tool's inputs are hostile", §4, come first); no card: `bad_card_chain`; card 0 does not
     hash to `--card0-hash`: `card0_mismatch`; the cards do not verify as one chain from card 0
     (spec 01 §5.2): `bad_card_chain`;
     card 0 names another instance than `--instance`: `instance_mismatch`; the newest card names no
     recovery key: `no_recovery_key`. Every rotation must verify from a key the history reaches (the
     cards' keys, then the keys verified rotations lead to): signed by the recovery key its `fromFp`
     names, with a good signature (`rotation_not_verified`), for `--instance` (`instance_mismatch`);
     a rotation from a key that nothing reaches is `rotation_chain_broken`. Then, from the newest card
     back, each key a card replaced is an **outgoing key** while the served rotations connect it to the
     newest card's key, the **current key**; when the change into the current key is not covered by
     rotations (an unsigned change), that is `rotation_chain_broken` too, and its sentence says that a
     copy sealed to the current key since needs no file. An older change that no rotation covers ends
     the list there, and the tool says that a copy sealed before it cannot be answered;
  2. the tool **says, before it asks for anything**, which sheet does what: the CURRENT sheet, by its
     fingerprint (32 hex in groups of four) and the time of the card that made it current, signs the
     answer; each OUTGOING sheet, by its fingerprint and the time of the card that replaced it
     ("outgoing since"), opens a copy the account has not sealed again since then. When the key never
     changed it says so: one sheet. A rotation already stored for which no card names the new key yet is
     said too: devices still take only the current key. **"Since" is the card's time, on both
     sides:** the moment a key became current, or outgoing, is the `issuedAt`
     of the card that first named the new key, because that card, not the rotation statement, is what
     moves every device to the new key and starts its re-seal; a rotation is stored before its card and
     may be days older. A device that shows a person that the server's recovery key changed while their
     request was open shows that same card's `issuedAt`, so the person's screen and the operator's
     "since" name one moment (the shared code gives the person the `issuedAt` of the first card that
     named the new key);
  3. the seed of the CURRENT sheet, asked for by that name (`bad_seed`); its key must be the current
     key (`wrong_sheet`). It is needed in any case: it signs the answer;
  4. a trial opening of the copy with it, which reads nothing of what it opens. If the copy opens, the
     tool says that the outgoing sheet is not needed and goes on as the one-sheet command does: one
     seed. Otherwise the tool says that the copy was sealed before the change, and asks for the seed of
     the OUTGOING sheet by its name and fingerprint (`bad_seed`; its key must be that outgoing key,
     `wrong_sheet`), newest first when there are several, until one opens the copy. A copy that opens
     with none of them is `unopenable`, with the sentence that it is sealed to no key of this server's
     history;
  5. §4 steps 1 to 9 with the sheet that opened the copy, so the copy's own signed statement must name
     that key as its `recoveryFp` (`recovery_fp_mismatch`); the display also says that the answer is
     signed with the CURRENT sheet. The chain from the opening key to the current key is verified once
     more, link by link, as a device follows it (`rotation_chain_broken`). The outgoing seed and its keys
     are wiped as soon as the copy is opened; the answer (§7 step 3, items 4 to 6) is signed with the
     current seed, and that seed is wiped after it.
- **What this does not cover.** A copy sealed to an outgoing key whose sheet is gone cannot be
  answered: no device takes another key's signature. Of several outgoing keys, the tool asks newest
  first, so it may ask for a sheet that turns out not to open the copy. The file is the server's word,
  in two ways:
  - **It can be withheld.** The first card's hash ties the chain to the server the operator knows,
    but not to its newest state: a server can serve its genuine chain cut short, or leave out a
    rotation. The tool then refuses, or names as current a key that is no longer the one devices take,
    and the answer it makes is refused by every device (availability only: the answer is sealed to
    the request key, and no device takes a signature that its pin does not name). In the fleet check a
    shortened chain makes copies on a later key `recovery_fp_mismatch` FAILs, never a PASS.
  - **Without the hash it can be made up.** With `--instance-file-unchecked` nothing ties the file to
    the server the operator knows: a made-up chain under the real instance ID can name any key as
    outgoing or current. What the tool still guarantees is that each seed is the sheet it was asked
    for by fingerprint (`wrong_sheet`), that every signed field of the answer comes from the command
    line or the opened copy, and that no device takes an answer its own pin does not name; what it no
    longer guarantees is that the keys it calls current and outgoing are the server's. In the fleet
    check, a key the made-up file calls outgoing makes its rows `SKIP`, not checked, never a PASS.
  Before the newest card is signed, devices take only the outgoing key, and the tool, given the file,
  says so and asks for that one sheet.

**Unsigned change** (the outgoing seed is lost, or someone else signed the card). No silent re-seal ever
happens. The app shows:

> **The recovery key for *name* (*origin*) changed without the old key's signature.**
>
> This can mean the operator lost the old key. It can also mean someone has taken over this server's
> identity. Keep operator recovery only if the operator has told you why it changed.
>
> [ Turn off operator recovery ] *(default)* [ Keep it with the new key ] [ Later ]

Both changes need the master password (`PUT /account/recovery`). [Later] changes nothing and seals
nothing; the prompt returns at the next unlock. A thief of the operator key can publish such a card;
every opted-in person then sees this prompt, which defaults to off (spec 05 R30).

**`recovery-cli`** is an offline-first fat jar (`tools/recovery-cli`): no network I/O ever
(compile-time — no HTTP client on the classpath); it refuses to run if it detects an andvari server URL
argument. Input/output via files + stdin/QR. Commands: `keygen`, `canary make` / `canary verify`, the
fleet `verify <seedFile> <escrowDumpJson>`, `assist` (§7), `rotate`, `fingerprint <pubkey>`. It uses
the same `:core` crypto as everything else, so the vectors pin its behavior too.

## 6. The recovery kit (per-member self-service recovery)

Every account has a kit, on every instance, in both postures. Crypto constants and the
generated-entropy invariant are spec 01 §2.1; the routes are spec 03 §12.

### 6.1 Why symmetric — and why T10 does not apply here

The kit's secret wraps the UVK with the AEAD `Envelope` (AD `andvari/v1|recovery-uvk|{userId}`), not a
sealed box: there is **no public key to substitute**, so spec 05 T10 does not apply to this path. The
worst a hostile server can do is serve a wrong `recoveryWrappedUvk` → the AEAD tag fails → recovery
**fails closed** (availability denial, accepted under T1). Because the secret is generated (256 bits)
and never typed into the KDF, it needs no Argon2id and is stronger than the master password; the
invariant that keeps it strong — generated, never user-influenced — is load-bearing (spec 05 T8).

### 6.2 The kit

- **The secret:** the 32-byte `recoverySecret` (spec 01 §2.1).
- **Display:** base64url, 43 characters, in **11 groups** (ten of 4, one of 3), separated by spaces.
  A typed kit secret ignores space, CR and LF only: a tab is not ignored, and a dash is **not**
  ignored, because base64url uses `-`.
- **Confirmation:** three distinct group indices chosen uniformly by CSPRNG from 1..11 ("Type groups
  2, 7 and 10"), compared exactly and case-sensitively once space, CR and LF around each typed group
  are ignored. After 3 failures the kit is shown again. There is
  **no Copy button** on the reveal or confirm screens. A correct confirmation calls
  `POST /recovery/self/confirm` with the kit's `pieceId` (spec 03 §12), which sets the durable
  `recoveryConfirmed` flag only while that id names the CURRENT kit; the vault-entry capture gate
  re-fires on every device until it is set.
- **The kit document** is generated on the device and never uploaded, offered as Print, Save to Files
  or Save PDF (whatever the platform offers without leaving a temporary copy behind). It contains: the
  title "andvari recovery kit"; "Keep this private. Anyone with this kit and your email address can
  reset your master password and open your vault."; the email, the instance name and origin, the date;
  the grouped secret, large and monospace; the kit QR; "Your account ID: <32-hex short identity
  fingerprint>" (the anchor of an assisted recovery, §4); and "To recover: open andvari → Sign in →
  Forgot your master password? → Scan your recovery kit".
- **Kit QR:** `andvari-kit:2:<O>:<C>:<E>:<S>` — `O` the unpadded base64url of the origin, `C` the
  instance's `card0Hash` as 64 lowercase hex, `E` the unpadded base64url of `emailNorm`, `S` the
  unpadded base64url of the 32-byte secret. It is deliberately not a URL, so a system camera does not
  offer to open it. Parsing is total and canonical, exactly as for links (padded or uppercase forms are
  refused): space, tab, LF and CR are stripped first, as from a link (spec 03 §15.1), except that the
  kit QR text may be up to **1,024** characters after the strip, not 512, because it carries a whole
  email address and an origin. A kit text that does not parse is `bad_kit`. `card0Hash` lets a fresh
  device pin the instance from card 0 at recovery time (spec 01 §5.3), so a self-hosted instance is never trusted on first use then. Vectors:
  `spec/test-vectors/recoverykit.json`.
- **Rotation:** "Make a new recovery kit" in Settings calls `PUT /recovery/self-setup` with a fresh
  `currentAuthKey` (spec 03 §12). Every setup, register and recovery commit mints a new `pieceId` and
  clears `recoveryConfirmed`, so the old kit stops working at once.

### 6.3 Recovering with the kit

- **Where a kit is accepted.** Only on **Sign in → Forgot your master password? → Scan your recovery
  kit**, by scanning or typing it there. "Scan an invite" and its paste field refuse kit payloads with
  "This is a recovery kit, not an invite.", with no directions, and start nothing.
- Before anything is sent, the recovery screen names the account and the server: "Recover *email* on
  *name* (*origin*)", with the email from the kit, and says that this sets a new master password for
  that existing account. Why: an attacker could otherwise sign up, keep that account's kit and show its
  QR as an invite; a victim who "recovered" it would live in an account whose keys the attacker holds.
- The client pins the card chain from the kit's `card0Hash` (this pin counts only for the kit's own
  account, spec 01 §5.3), runs the two-phase recovery (spec 03 §12: verify, then commit), and sets a new
  master password. `recover()` routes the phase-1 unwrap through the shared UVK-unlock tail, so the
  seed-derived identity-pubkey hard-fail (spec 01 §5) still fires, and never regenerates UVK, identity
  seed or identityPub.
- **The commit replaces the kit**: it carries `newMemberRecovery` from a fresh secret, and in the same
  transaction the server replaces the member-recovery row, so the scanned kit stops working at once.
  The app shows the new kit through the capture gate before the vault opens. The commit also revokes
  every session, **clears two-step sign-in** (sending `two_step_off`) and clears "New devices must be
  linked". So an attacker who handed over a kit cannot use it again later; against an honest server the
  session revocation locks them out.
- **Anti-enumeration.** `POST /recovery/self/verify` is timing/shape-uniform across all three states —
  no such email / known email with no kit row / known email with a row — running a fixed
  `DUMMY_RECOVERY_VERIFIER` on the first two and returning a bare uniform `401` for every failure. No
  `/recovery/prelogin` exists.

## 7. Operator-assisted recovery (private instances)

For an operator-posture account on a **private** instance, when the person has lost the master password
**and** the kit. It is absent on the public instance (variant R: every route answers `404`, spec 03
§18.6). No temporary password exists at any point. An emailed code alone authenticates only the inbox,
so a request has to survive four checks: a **7-day hold**, during which the account's signed-in
devices can **cancel** it; a **request code** that the person reads to the operator over a channel the
operator trusts; a payload **signed by the offline recovery key**, so no server can fake the operator's
answer; and copy that says plainly who can ask.

1. **The person asks.** On a fresh install, "I lost my master password **and** my recovery kit" → "Ask
   the operator for help". The screen says: "Anyone who gets into your email can ask too. The operator
   waits 7 days and checks with you, and your other devices can cancel." The app makes an X25519 pair
   `(rPub, rSec)` and a 32-byte `pollSecret`, kept in device state protected like a session until
   commit, veto or 30 days, and opens the request (spec 03 §18.1). It shows the **request code**
   `hexLower(SHA-256("andvari/v2|recovery-request|code|" + b64url(rPub)))[0..24]` as six groups of four
   (96 bits): "Read this to the operator when they contact you."
2. **The person proves the address** with the emailed 6-digit code (spec 03 §18.2). The hold starts.
   A request the account's owner cancelled before its code was entered (a password change, a switch to
   "Only me", a recovery) is told so only here, and for the device that asked it is a final stop: it
   forgets the request and says why, and a new request can be started (spec 03 §18.4, which says what
   the shared code does not keep of this yet).
   Every signed-in device of the account shows "Someone asked the operator to reset your account. If
   this wasn't you, cancel it." Cancel posts a 0x0A veto signed by the account key (spec 03 §18.3). The
   account's email gets a notice with the time and platform, and **no account ID** (spec 03 §14.5:
   the mails about a request carry none, so a person never takes the server's word for it as an anchor).
3. **The operator acts, after the hold and outside the server.** They contact the person through a
   channel they already had, independent of the server and the inbox (on a family server: in person, or
   a number they already know), and ask for the request code and, if possible, the account ID. They
   already know the person's **address**: knowing whom they are helping is the point of this step.
   The panel and `andvari-cli operator` **never display the request code**, and **nothing the server
   says is offered as something to check against** (rule of 2026-11-16): they show a request's id and key (the
   tool needs both; a swapped key is caught by the code the person reads out) and the address the
   request was made for, never the server's account ID as a value to copy, and no sentence tells the
   operator to copy one. Every field of a request row is checked against its grammar before it is shown
   or copied (spec 03 §18.6). On an offline machine:
   `recovery-cli assist --instance <uuid> --request <requestId> --request-key <rPub> --request-code <code>
   --email <the person's address> --user <uuid> (--identity-fp <32+ hex> | --no-identity-anchor)
   --identity-file <escrow-download.json>`.
   `--instance` is the instance id from the card: the 0x09 statement names the instance, and the tool is
   offline. `--email` is the address the operator TYPES from their own knowledge of the person (rule
   of 2026-11-16); a y/n question or a value offered for copying does not replace it. The tool runs, in order, the
   first failure stopping it with nothing produced:
   0. the command line itself, as it is read: an option `assist` does not have (`unknown_option`), the
      old `--legacy` switch (`legacy_refused`), an option given twice (`repeated_option`), more than one
      copy given (`more_than_one_copy`); see
      §4 "Two layers";
   1. its own three request arguments, in this order (absent or malformed), each **exactly as given**,
      nothing removed (an id or a key with white space around it is malformed): `--instance` a lowercase
      uuid (`bad_instance`); `--request` a `b64_16` (`bad_request_id`); `--request-key` a canonical
      `b64_32` (`bad_request_key`) that is not a low-order point (`low_order_request_key`); then §4
      step 0, in its order. The values checked are the values the answer carries;
   2. `--request-code` present and equal to the one it computes from `--request-key`
      (`request_code_mismatch`; this stops a server that swapped `rPub`), **before** it reads the
      identity file or asks for the recovery seed. A person reads the code out and another types it,
      so the command line removes spaces, tabs and dashes from what was typed and compares its letters
      without regard to case; any other character (a line break, a no-break space) is no match. Then
      the clock, with the arguments and before anything is read: `issuedAt` (item 4) must have exactly
      13 digits, `10^12 <= t < 10^13`, or the tool refuses to run (`bad_clock`). The time it checked
      here is the time the answer signs;
   3. §4 steps 1 to 9: the copy must be version 3 (`no_address`) and name the typed address
      (`email_mismatch`), and the operator types `RECOVER <first 8>` having seen the address the copy
      names (`not_confirmed`). When the account has not sealed a new copy since a signed rotation, its
      copy is sealed to the outgoing key: the operator adds `--instance-file` with the server's
      `GET /api/v1/instance` answer and `--card0-hash` with the hash of its first card, which the
      operator holds, and has both sheets at hand; the tool checks the file from that hash before any
      seed is asked for, says which sheet opens the copy and which signs the answer, opens with the
      outgoing seed and signs with the current one (§5, "A copy sealed to an outgoing key");
   4. a fresh **commit value** `commit`, 32 bytes from the CSPRNG, and the 0x09 statement,
      **version 3**:
      `{"v":3,"purpose":"assisted-recovery","instanceId":<uuid>,"userId":<uuid>,"email":<email_b64>,"requestId":<b64_16>,"requestKey":<b64_32>,"commit":<b64_32>,"uvk":<b64_32>,"issuedAt":<ms>}`,
      keys in exactly this order: `userId` = `--user`; `email` = the copy's own `email` field, copied
      byte for byte (step 8 proved it is the typed address); `requestKey` = `--request-key`; `commit` =
      `b64url(commit)`; `uvk` = the copy's key; `issuedAt` the tool's clock in ms as item 2 checked it
      (exactly 13 digits, `bad_clock` otherwise). **Signed by the
      recovery-key signing key** and sealed with `crypto_box_seal` to `rPub`. With `n` the octets of the
      address and `E = ceil(4n / 3)` the length of its unpadded base64url, the statement is
      `376 + E` bytes, the frame `477 + E` and the sealed answer exactly **`525 + E` bytes** (548 for a
      17-octet address);
   5. the **commit hash** `commitHash = hexLower(SHA-256("andvari/v2|recovery-request|commit|" + b64url(commit)))`;
      the commit value itself is never printed, and is zeroed once sealed;
   6. the output, whose **last line is the answer token**, with nothing after it on standard
      output: `andvari-answer:3:<requestId>:<requestKey>:<commitHash>:<sealed>`, where `<requestId>` and
      `<requestKey>` are as given, `<commitHash>` as in 5 and `<sealed>` the unpadded base64url of the
      sealed answer. None of the four parts can contain `:`. The lines before it name the request, the
      account and the address, and say that only the person's device can open the answer.

   The operator uploads the token (`fulfil`, spec 03 §18.6) from the console or with `andvari-cli
   operator fulfil`; both read it with the one shared reader below, before the master password is
   asked. The server refuses before the hold has passed or after a veto, an upload whose request key is
   not the row's, and a sealed answer of any other size than the one for the request's address. Until
   the commit the operator may upload again, with the master password each time; the newer answer and
   commit hash replace the older.

   **Reading an answer** (the desktop console and `andvari-cli operator fulfil` share one
   reader: there is no operator console in the web app, whose operator sessions the server refuses).
   Its input is the operator's text (a paste, or a file's bytes read as UTF-8: bytes that are not UTF-8
   are `not_an_answer`) and a listed request whose row passed its grammar: `requestId`,
   `rPub` and the address the request was made for. "Base64url characters" are `A`-`Z`, `a`-`z`,
   `0`-`9`, `-` and `_` (never `=`). In order, the first failure deciding:
   1. drop U+FEFF when it is the text's first code point (only there); split into lines at CR LF, LF and
      CR only; remove space and tab (only those) from both ends of each line; drop empty lines. None is
      left: `answer_empty`;
   2. the first line begins with `{`: `answer_is_the_copy` when the text (all of it after a dropped
      U+FEFF, case-sensitive, quotes included) contains `"encryptedIdentitySeed"` or `"identityPub"`
      (the recovery copy, which the tool reads), otherwise `not_an_answer`;
   3. the lines that begin with `andvari-answer:`: more than one is `not_an_answer`. Exactly one: the
      lines before it are passed over, whatever they hold; the token is that line followed, with nothing
      between, by every line after it, each of which must be base64url characters and `:` only (a
      terminal may wrap a long line, inside the token's head as well as inside its sealed part), else
      `not_an_answer` (a shell prompt after the token, say; the words say to copy only the last
      line the tool printed). None: when every line is base64url characters only and they hold at least
      **100** characters together, `answer_bare` (a sealed answer without its request, as the old tool
      printed it, or a token's tail: longer than an id, a key or a hash, shorter than any sealed
      answer); otherwise `not_an_answer`;
   4. the token split at `:` has exactly six parts: `andvari-answer`, `3`, a `b64_16`, a `b64_32`, a
      `hex64` and a non-empty run of base64url characters; otherwise `not_an_answer`;
   5. the third part is not the request's id: `answer_other_request` (the reader names the id the token
      carries); the fourth is not the request's `rPub`, compared as text: `answer_other_request_key`;
   6. the size: the sixth part is canonical unpadded base64url of exactly `525 + E` bytes for the
      request's address. Otherwise, with `L` its decoded length when it is canonical and
      `floor(3 * characters / 4)` when it is not: `L` smaller is `answer_cut_short`, larger
      `answer_too_long`, equal `not_an_answer`. The words for the first two say both possibilities: the
      answer is cut or damaged, or it was made for another address. An answer made for
      another address of the same length passes the reader; the device refuses it (step 4).

   The reader yields the four parts, and a client uploads exactly those. Nothing is sent and no password
   is asked for a refusal. It is a convenience, not a boundary: the check inside the seal on the
   person's device stays the authority.
4. **The app picks it up** (spec 03 §18.4) and requires, in order: the seal opening with `rSec`
   (`unopenable`); the 0x09 frame and strict parse, with spec 01 §5.1's verdicts in its checking order
   (`bad_frame` for a frame under four bytes, `unknown_format`, `bad_frame`, `non_canonical`,
   `bad_statement`). The reader tries both templates of 0x09: the key set picks one, and the version
   this section does not accept is `bad_statement`. So a statement canonical under the old
   version-2 template, which has no `email` and no `commit`, is `bad_statement` whatever its `v`, and a
   version-3 key set marked `"v":2` is `bad_statement` too: a device takes only a version-3 answer. Then
   the **signer mapping to the recovery public key the pinned card's `recoveryFp`
   names** (`signer_not_pinned_key`): no server can sign an answer without that recovery key, but on a
   fresh install pinned by typed address the pin is whatever card chain the server served, so this binds
   only a server that does not hold the key the pin names (see "What these checks do not cover"); the
   signature (`bad_signature`); then `instanceId`, `userId`, `requestId` and `requestKey` matching, and
   `email` decoding to exactly the `emailNorm` of the address the person typed when asking, **on a
   fresh install too** (`request_mismatch` for any of them); and the identity seed opening under the
   delivered UVK to a key equal to the served `identityPub` (`identity_mismatch`, also when the seed
   does not open under that key at all). A device that holds no `userId` (a fresh install) skips the
   `userId` comparison, because the identity seed's AD binds it. The device keeps the `commit` value
   with the delivered key, in memory only, until the commit or until the person leaves. Vectors:
   `spec/test-vectors/recovery.json` (the old form) and the version-3 rows added beside it.
5. **The person sets a new password** (spec 03 §18.5). The commit carries the `commit` value from the
   answer the device opened; the server refuses a value whose commit hash is not the one
   stored with the newest upload (`403 commit_mismatch`), so a reset is accepted only from a device that
   opened the answer. A device told `commit_mismatch` drops what it opened and keeps its request, and its
   next poll picks up the newer answer. The commit replaces the kit in the same transaction, revokes
   every session, clears two-step sign-in and "New devices must be linked", and emails "your master
   password was reset with the operator's help". The app shows the new kit through the capture gate
   before the vault opens.

**Limits.** Per IP for opening requests; per address for the emails (5 per window of 24 hours that
starts at the first mail it counts); for verify attempts, 5 per request, with requests themselves
capped at 5 per address per window of 24 hours, and no cap per address on the attempts, because one
let a stranger's wrong codes on a request of their own use up the owner's.
**Past the cap, through the mailbox** (decided on 2026-11-17; spec 03 §18.1 has the nine points):
the code mail of every request carries a mailbox value (sixteen symbols, 80 bits; the field is
`mailboxValue`; a typed value is brought to its form in ASCII only, and any character outside the
alphabet but a space, a tab, a dash or a letter a to z makes it a wrong value), and a request that
names an unused, unexpired value of that address is taken as a real one even when the address's
five of its window are spent, with a ceiling of its own of five per window and a mail budget of its
own of five per window. The two windows run independently: within one window of each an address
receives at most five plus five request mails, and across their edges up to twenty inside 24 hours,
more than ten only through requests that name values. A request for an account in the private
posture never uses a value. A wrong, used, expired or foreign value changes nothing, and the answer
and its timing are the same whatever value is sent. A stranger who knows the address can therefore
no longer keep its holder from asking for help; a person who cannot read the mailbox still cannot
ask, and someone who reads it can spend both caps themselves (spec 05 R37). The server keeps it in
full; what the shared code does not keep yet, and the apps' field and the command-line option that
do not exist yet, are listed in spec 03 §18.1 (2026-11-17). The
verify route also has a bucket per caller address of its own name, `recovery_request_verify`, 20 an
hour (spec 03 §18.2), and every refused code is recorded (`recovery_request_verify_fail`), naming the
account only for a real request, so a decoy answers exactly like a real one. A wrong commit value
changes nothing about the request: it is audited, the commit route keeps its per-IP bucket, and the
right value still commits (spec 03 §18.5). The poll secret is checked first
(`404 request_unknown` for anyone else), so only the holder of that request's secret reaches the
comparison at all. Against an honest server a request in a victim's name does nothing without the code from the
victim's inbox, the 7-day hold, the person's own confirmation to the operator, and no veto.

**What these checks do not cover, and what they now do.** The hold, the
veto and the emailed code bind only an honest server.

- **An answer uploaded to the wrong row** (two requests for one address, the right answer pasted
  into the other row) is refused by the reader and by the server, because the token and the upload
  carry the request key; and, forced past both, it cannot be committed by the other row's holder, who
  cannot open it and so does not have the commit value. Against an honest server, an email-holder who
  never opens an answer cannot replace the account's password.
- **Another member's copy under a request.** On a server whose host is the attacker, the
  server may put any account's recovery copy, user id and account ID under a request. The operator's
  typed address stops it: the copy that opens must name, in its own account's signature, the person
  the operator is helping (§4 step 8). So a host member who asks for help in their own name, reaches
  the operator truthfully on their own number and reads out their own real code gets their own account
  and nothing else; and the person's device refuses an answer for another address than the one they
  typed (step 4).
- **What remains.**
  - The operator's knowledge of whom they are talking to. Someone who convinces the operator that they
    ARE the person, under that person's address, through the operator's own channel, gets that person's
    account. Only the operator's own check, through a channel they already had, stands in the way
    (spec 05 R27). That is natural on a family server and absent for strangers, which is why the public
    instance has no operator recovery.
  - A server that is itself the attacker can still open a request with its own key, mark it verified and
    its hold passed, and suppress the bell and the mail; it still needs the operator to help the person
    it names, as above.
  - On a fresh install pinned by typed address (the usual device for this flow), a hostile server can
    serve a card chain of its own, whose recovery key it holds, and answer the request itself with a
    minted account that claims the person's address. The person's comparison of the delivered account
    ID with their own (step 4) is then the only check, and only when the person holds an account ID
    that did not come from this request (below); a device that held the real account refuses that
    identity at its next unlock only while the server keeps the same user id (below).
  - A copy of the old form cannot be checked against an address and is refused; only a person who can
    still sign in somewhere can seal a new one (below).

**What these checks still do not cover** (in plain words; each is a limit of the
design as it stands, not a promise of a later fix):

1. **The account ID is often the server's own word.** Without the kit, the only account ID a person
   holds is one this server mailed them; the request's own mails no longer carry one (spec 03
   §14.5), but every earlier notice did. An emailed notice
   counts as a source for the account ID only if it is **older than the request**; the kit is the
   better source. For a person with neither a kit nor an older notice, the comparison of account IDs
   (§4 step 2, step 4 below) is **void**, and the operator's own knowledge of the person is the only
   check.
2. **A minted identity under a new user id is refused by no device.** The earlier devices' "first
   identity seen" record is kept per user id; a server that answers with a fresh user id under the same
   address is not caught by it, so the claim that every earlier device refuses a minted identity holds
   only while the user id stays the same.
3. **A recovery-key change during an open request.** A change not covered by rotation statements is
   followed silently by a device with an open request. After a signed rotation, an account that
   has not sealed a new copy since holds a copy sealed to the outgoing key, while the devices take only
   answers signed by the new one: the two-sheet `assist` of §5 answers it, for as long as the operator
   keeps the outgoing sheet, which the fleet check says when to destroy. A copy whose outgoing sheet is
   gone cannot be answered. The server's `GET /api/v1/instance` answer that both commands take is
   checked from the hash of the first card, which the operator holds; it can still be withheld or cut
   short, and with `--instance-file-unchecked` it can be made up (§5, "What this does not cover"). The
   fleet check's line about destroying an outgoing sheet covers only the accounts in the dump.
4. **The veto needs a device the person opens during the hold.** The shared code reads the sync's
   count of requests and raises the alert, and its list keeps a request the operator already answered,
   so a veto stays possible until the commit (spec 03 §18.3); a person who opens none of their
   signed-in devices in those seven days does not see the request.
5. **Wrong commit values.** They no longer cancel the request: each is audited and the right value
   still commits (spec 03 §18.5). The poll's answer carries the stored commit hash, and the shared code
   compares it with the hash of the commit value it opened before it asks its person for anything, so a
   replaced upload is said then, not only at the commit; a poll answer without the field (an older
   server) leaves it to the commit.
6. **The token is not authenticated.** The reader and the server judge its shape only: a token with
   one hash digit changed is read and stored; only the device's check inside the seal and the commit
   value bind an answer to its request.
7. **An old-form copy cannot be replaced by the person who needs it.** Turning operator recovery off
   and on needs the master password; a person who has lost it and has no signed-in device cannot seal
   a new copy, and the operator cannot recover that account.
8. **A stolen outgoing seed with a withheld card.** A device that never saw the rotation accepts an
   answer signed by the retired key.
9. **The address shown for a request is the server's.** The operator types the address from their own
   knowledge; the one the console shows beside it is only what the server says.
