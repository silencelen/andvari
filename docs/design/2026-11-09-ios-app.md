# iOS app: native client, AutoFill and Safari extension

Status: accepted, in progress. Replaces the earlier idea of a small iOS carrier app for the Safari extension.

## Goal

One App Store app with three parts:

1. A complete native password manager.
2. System-wide password AutoFill (a credential provider extension).
3. The Safari web extension.

It follows the self-hosted model of the other clients: the user points it at their own server.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| UI | SwiftUI over the shared Kotlin core | AutoFill must be native anyway, and Face ID, secure text fields and accessibility are first-class. The Android and desktop UIs cannot be reused. |
| Shared logic | Move platform-neutral session logic from the Android app into `core` | The security rules (auto-lock clamps, quick-unlock freshness, the trust gate, origin namespacing) should exist once, not once per platform. |
| Kotlin to Swift bridge | A small hand-written facade in `iosMain`, exported through the normal Objective-C interop | No third-party compiler plugin in the build of a password manager. |
| Crypto | Official libsodium, built from its signed release at a pinned hash, through cinterop | Same library as every other client. No third-party wrapper. |
| CI | Compile and test in this repository with no secrets. Signing and upload happen in a separate private repository | Signing material never reaches a workflow that runs public code. |
| Minimum iOS | 17 | Current credential-provider APIs, and a small test matrix. |

## Phases

1. **Core on iOS.** `iosArm64` and `iosSimulatorArm64` targets. The acceptance test is `spec/test-vectors` passing on an iOS simulator.
2. **The everyday app.** Choose a server (with the trust gate), sign in, enroll, unlock, browse, search, add and edit, generator, one-time codes, Face ID, auto-lock, offline cache.
3. **AutoFill.** Logins offered above the keyboard and in the system password list.
4. **Parity.** Sharing and household, trash, health, recovery, import and export, cards.
5. **Store gates.** In-app account deletion, a demo server for App Review, the export-compliance answer, listing assets.

## Core on iOS

The `expect` surface is small: `createCryptoProvider`, `openSqlBox` and `nfc`, plus the Ktor Darwin engine.

- `SodiumCryptoProvider` mirrors `LazySodiumCryptoProvider` guard for guard. The exception type on each guard is part of the contract, because the unlock ladders classify on it.
- HMAC and SHA use CommonCrypto, as the JVM adapter uses `javax.crypto`.
- `NativeSqlBox` uses the system SQLite with the JDBC actual's connection settings.
- Code in `jvmShared` that is only there for a small JVM dependency moves to `commonMain`, using multiplatform locks.
- Vector tests move from `jvmTest` to `commonTest`, so the same assertions run on JVM and iOS.

Kotlin moves to a release that supports Xcode 26, which App Store Connect has required since 2026.

## Session layer

Android and desktop each carry their own copy of the session flows, and the copies have drifted. The shared layer moves into `core` one step at a time. Android switches to each step as it lands, and desktop follows.

The platform supplies a small set of interfaces: persisted session state, per-origin stores, namespace directories, clocks, quick-unlock key wrapping, HTTP clients and transport rules. Tests that pin the Android source text move with the code they pin.

Decisions for the iOS client:

| Question | Decision |
|---|---|
| First launch | No default server and no probe. The user chooses a server, through the Trust Gate. |
| Offline cache | Allowed until the server's policy forbids it, as on Android. |
| Leaving the app | The vault locks when the app goes to the background, as on Android, because a suspended app cannot run an idle timer. |
| Invite links for another server | In v1 the user switches server through the manual Trust Gate first, then enrolls on that server. The invite-driven pending switch comes later. It is the riskiest part of the move, because Android and desktop give the pending marker opposite meanings. |
| Boot identity | Spec 01 §8.1 requires one the device holder cannot set. iOS reads `kern.bootsessionuuid`. If that is unavailable, every check takes the cross-boot path, so Face ID needs a server contact newer than the last password unlock. This fails closed. |
| Monotonic time | A clock that keeps counting during device sleep (`CLOCK_MONOTONIC` on Darwin). `ProcessInfo.systemUptime` stops during sleep and must not be used. |

## AutoFill

iOS runs the extension in a separate process, with a tight memory limit, and can suspend or kill it at any time. That rules out sharing a live session as Android's in-process service does.

**The extension never contacts the server.** The account has a single token holder, and refresh tokens rotate. A second process that refreshed could reuse a consumed token and revoke the device.

**The extension reads an encrypted snapshot.** After each sync the app writes the wire rows it needs, still encrypted under vault keys, to one file in the App Group container, replacing it atomically. The extension only reads it. This avoids sharing SQLite across processes, where a file lock held during suspension gets the process killed (`0xdead10cc`). No snapshot is written when the server's policy forbids an offline cache; the extension then asks the user to open the app.

**Unlock is Face ID only.** A password unlock costs at least 64 MiB of Argon2 by default, and up to 256 MiB, which is unsafe inside the extension's memory limit. The extension obtains the vault key through the same Secure Enclave-wrapped blob the app's quick unlock uses, holds it only for the fill, and zeroes it. If quick unlock is off or has expired, the extension asks the user to open the app.

**The system identity store** (`ASCredentialIdentityStore`) needs domains and usernames in the clear, on the device, to offer logins above the keyboard. It never holds passwords. It is populated from the unlocked app and cleared on sign-out, and the user can turn it off, which leaves the password list as the fill path.

**What the extension trusts, and the revocation window.** The extension fills only for the account whose session is stored now: it reads the stored session's identity (never its tokens) and ignores a snapshot that names another account or server. The snapshot holds only the login items the app itself shows; the app's trust decisions about vaults and keys are not re-made in the extension. Because the extension never contacts the server, it cannot learn that the server revoked this device: it keeps filling from the last snapshot until the app next runs, hears the rejection and purges the snapshot and the quick-unlock key. The freshness gates bound that window: quick unlock needs a master-password unlock within its window and a policy seen within 7 days.

**Threat note: the snapshot's account keys.** The snapshot carries the account's key material as the server stores it (KDF salt and parameters, the wrapped UVK, the encrypted identity seed). That is what an attacker needs to guess the master password offline. It was already on the device in the app's own container, as the offline-unlock cache; the App Group makes it readable by the AutoFill and Safari extension processes as well, so a compromise of either extension now reaches it.

**Saving.** Neither extension can write to the vault: they hold no token and no vault key. A captured login is sealed (libsodium sealed box) to the account's public identity key, which the unlocked app publishes to the App Group, and queued there as a small file. The queue is bounded (50 entries of at most 8 KiB), holds no plaintext, and is emptied on sign-out, on a server switch and when the server's policy forbids keeping data on the device. At its next unlock (and when it returns to the foreground unlocked) the app opens the entries and drops any that are not sealed to this account at this server.

**What is saved without a second tap (owner decision, 2026-11-11).** The person already agreed to the save, in the system's prompt or the extension's, so the app applies it by itself and then says what it did: a "Saved N logins from AutoFill" list, with Undo for each and Undo all. Anything that can write to the App Group can queue an entry, so a forged entry would otherwise be a silent vault write. What is automatic is therefore bounded:

- A new login is added to the personal vault.
- A new password replaces an existing one only in the **personal vault**: never in a vault shared with the person, and never in one they own and share out (until the owner decides otherwise, those are treated alike). The login is matched by host, port, scheme and username. The capture must be newer than that login's last change and not dated in the future, its scheme must be known (a capture that names only a domain is never applied over a login by itself), and a login is replaced at most once per unlock. The password it replaces is appended to the login's `passwordHistory` (spec 02 §3), which keeps each earlier password once and at most 20.
- At most 5 captures are applied per unlock or return to the foreground. Captures are taken oldest first by their capture time, and an older capture of the same login is dropped for the newest.
- Everything else stays listed with its reason and where it came from, with Save and Discard.

The list of what was applied is kept across a lock, sealed to the account in the app's own container (not the App Group), until the person dismisses it; Undo works after the next unlock too. Undo is exact: a login the save added is removed only if it is still as it was added (the id was minted by the save), and a replaced password is put back, and its history entry taken out, only if the login still has the password the save wrote. One mutex serializes reading the queue, applying, a save by hand and an undo.

On iOS before 26.2 the save prompt is the extension's own, drawn in the page, so a page can try to steer a click onto its Save button; what such a click can cause is bounded by the rules above (a new login, or one newer password for a matching personal login, listed and undoable).

The iOS app shows a login's password history in its detail, newest first.

A capture older than 30 days is dropped unread. Each capture is queued under its own random id, so a later one never replaces one the person was told is on its way; the app drops a capture whose login the vault already holds. The row in the app shows the scheme of a capture made on a plain-http page, saves it as an http address, and never treats it as the https login of the same host. A save writes what was matched when the entry was opened: the login it replaces is fixed then (one of the person's own vaults, never a vault shared with them), and if that login changed in between, nothing is written and the entry is listed with that reason.

**The published key is not authenticated.** It is a file in the App Group, so a compromised extension process could replace it with a key of its own; logins captured afterwards would be sealed to that key, which means whoever replaced it can read them, and the account cannot. The app checks the file against its own identity key at every unlock, puts it right, removes what it cannot read and says so. That limits the exposure to captures made in between; it does not undo it. A MAC held in the app's private Keychain group would not help the extensions, which could not verify it; it was not added.

**No sign at the moment of saving.** The system's save request completes without any interface of ours, and the API offers none short of asking for user interaction on every save. The app does not ask for notification permission, so there is no notification either. The save lands in the vault the next time the app is unlocked, and the list of what was saved is the cue. Until then the new login is not in AutoFill's suggestions.

Two things feed the queue:

- **iOS 26.2 and later: the system's save request.** A credential provider that declares `SupportsSavePasswordCredentials` receives `performWithoutUserInteractionIfPossible(savePasswordRequest:)` with an `ASSavePasswordRequest` and answers with `completeSavePasswordRequest(completionHandler:)`. The AutoFill extension queues the login from there, in Safari and in apps. On these versions the Safari extension captures nothing and shows no save prompt, but only while andvari is the enabled AutoFill provider: the app publishes that state to the App Group whenever it comes to the foreground, and without it the system would never call the extension, so the web extension's own prompt stays.
- **iOS 17 to 26.1: the Safari extension.** It captures the login in the page, shows its save prompt, seals the login itself and hands the ciphertext to its native handler, which only writes the file. Outside Safari the user adds logins in the app.

## Safari extension

On iOS the Safari extension has no sign-in, no session and no vault of its own. An earlier build had; the first start of this one signs that session out and removes what it stored.

- **Server:** the extension uses the app's server, read from the App Group by its native handler.
- **Fill in the page:** the system's AutoFill does it. The extension's in-page login menu is not in the Safari build.
- **Fill from the popup:** the popup's one button asks the native handler to unlock. The handler runs Face ID with the shared Secure Enclave key and opens the app's snapshot through the same read-only core object as the AutoFill extension: the app's quick-unlock gates, no network, no password KDF, no tokens. When a gate refuses (signed out, another server, a forbidding policy, Face ID off or expired) the popup says what to do in the app.
- **Save:** on iOS 26.2 and later the system's save request; before that the extension's prompt. Both feed the sealed queue (see Saving).

**How long an unlock lasts.** One Face ID opens the vault for 90 seconds. The handler keeps the opened vault in its process for that long (a monotonic deadline, checked at every use) under a random ticket it returns to the worker; the worker keeps the list of logins (no secrets) and the ticket in memory for the same time. Lock, the deadline, or a new unlock wipes both. The unlock is deliberately not tied to the popup: on iOS the system's Face ID sheet dismisses the popup, so the popup that asked is usually gone when the answer arrives, and the person opens it again to find the list. (A build that locked when the popup went away asked for Face ID on every opening and never showed a list.) The popup paints its unlock view first and asks for Face ID only two frames and 400 ms later, so the system sheet is not raised while Safari is still presenting ours. iOS may end the handler's process between two messages; a request for a secret then finds nothing open and the handler runs Face ID again itself, with a prompt that names the login, so the fill completes with a second prompt. No key and nothing decrypted is ever written to extension storage or to the App Group.

**Trust boundary, hop by hop.** This path has had no adversarial review. What each hop can ask the next for:

| Hop | Can ask for | Cannot |
|---|---|---|
| Web page → content script | Nothing directly. It can present forms, which the content script reports, and submit them, which is captured for a save (before iOS 26.2 only). | Trigger a fill, read a list, or see a fill happen other than as values arriving in its own fields. |
| Content script → worker | `reveal` for one item id. It is answered only when the top frame redeems the popup's one-shot grant, bound to the origin the popup saw; a matching address alone releases nothing, because this build has no in-page menu that would need it. The answer is a username and password, never a one-time code. Captures and page reports. | List logins (`allItems` and `matches` answer nothing to a page frame), unlock, read a one-time code, or name its own host. |
| Popup → worker | Unlock, the list (names, usernames, addresses), the logins for the active tab's site (by the tab's own URL), fill the active tab, copy one login's password or one-time code, lock. Filling a login saved for another site needs a second, explicit confirmation that names both hosts. The sender gate admits these from extension pages only. | Any vault write: none exists in this build. |
| Worker → native handler | `vaultOpen`: Face ID, then names, usernames and addresses. `vaultSecret`: one thing of one login by item id, either its username and password or its current code, never both, with the ticket or a fresh Face ID whose prompt names the login (the handler checks the name against the item before releasing anything). `vaultClose`. Also the server origin, the save key and a queue write. | A list with secrets, a key, or a token: the handler has no message that returns one. |
| Native handler → shared state | The snapshot, the shared defaults and the quick-unlock key, read-only, through the core. | The session tokens (the app's private Keychain group) and the server (its client refuses every request). |

What a reviewer should attack: the handler answers any native message from this extension, so every decision about *who may ask* is in the worker (the sender gate and the reveal gates). A compromised worker can ask for every secret, one item at a time, while a ticket is live, and can raise Face ID prompts. A compromised content script is held to the two `reveal` rules above. The item ids in the list are stable, so a ticket and an id are all `vaultSecret` needs.

## Manual checks with no automated test

These are Swift-only behaviours; the simulator job builds them but nothing runs them.

1. **Suggestions follow the policy (AppModel).** Unlock the app with suggestions showing above the keyboard in Safari. Set the server's policy to forbid the offline cache, pull to refresh in the app, then check that the keyboard no longer offers andvari logins. Allow it again, refresh, and they return.
2. **Suggestions never survive a sign-out (CredentialIdentities).** With many logins, unlock the app and sign out at once, several times in a row. After each sign-out the keyboard offers no andvari login, also a minute later.
3. **A fill ends once (CredentialProviderViewController).** Start a fill from the password list and switch away from the app while Face ID is up: the sheet is gone on return and nothing is filled. Start another and leave the unlocked list open for two minutes: it closes by itself. Tap a suggestion offered for one site while on another (a saved login whose address was edited in between): the list opens instead of filling.

## Quick unlock

The Android design carries over: wrap the vault key, never the password; every failure ends at a working biometric or the master-password prompt; freshness rules per spec 01 §8.1.

The wrapping key is a Secure Enclave P-256 key, created with `biometryCurrentSet` so that enrolling a new face invalidates it. The wrapped blob and key are in a Keychain access group shared with the AutoFill extension, marked this-device-only. That group is the App Group itself: Apple documents app group names as valid Keychain access groups with no extra entitlement, and a device test on 2026-11-11 confirmed it holds for a Secure Enclave key with `biometryCurrentSet`, read from the AutoFill extension.

## Other platform rules

- **Updates:** App Store only. The self-update channel stays off.
- **Clipboard:** local-only items with an expiry, so a copied secret does not reach Universal Clipboard.
- **Auto-lock:** measured on a monotonic clock, as on Android, with the same client-side clamp on server policy.
- **App switcher:** the UI is covered when the app leaves the foreground.
- **Transport:** HTTPS, with Apple's local-networking exception for LAN servers. No global exception.
